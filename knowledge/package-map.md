# Package map — podman-desktop

Which package owns what, which layer it belongs to, and what that implies for
review and merge order.

> Stub. The machine-readable map is generated by `pdkit init` from
> `pnpm-workspace.yaml` and lives in `$PDKIT_HOME/package-map.json`. This file
> holds what a generator cannot know: intent, boundaries, and the reasoning.

## Layer order

```
extension-api → main → preload → renderer + ui → extensions/* → tests → website/docs
```

This order does two things at once, and both matter:

1. **Merge order.** Lower layers land first, because upper layers depend on them.
2. **Reviewer selection.** The people who review a public API change are not the
   people who review a UI change. A PR spanning both waits for both.

## Packages

| Package | Layer | Owns | Notes |
|---|---|---|---|
| `packages/extension-api` | extension-api | the public contract for extensions | any change is a compatibility question |
| `packages/main` | main | Electron main process, plugin system, container engine plumbing | |
| `packages/preload` | preload | the bridge between main and renderer | |
| `packages/renderer` | renderer | the application UI | |
| `packages/ui` | ui | shared components | |
| `extensions/*` | extensions | bundled extensions | |
| `tests/playwright` | tests | end-to-end tests | |
| `website` | website | documentation site | |

## Boundaries worth knowing

Utilities get duplicated between `packages/main` and `packages/renderer`. Before
writing a helper, look for it in both — reviewers do, and they push back.

## What to add here

A boundary that turned out to be different than assumed, or a package whose name
does not predict its contents.
